# 知行 ZhiXing——一个会说也会做的个人事务智能体

> 「知」是理解，「行」是执行。  
> 这个名字就是我们这次作业的全部答案：一个智能体必须同时具备语言理解能力和工具执行能力，  
> 才算真正"智能"。

## 一、需求描述

### 1.1 背景与痛点

作为软件工程专业的学生，我们每天被这些琐事切碎注意力：

- 课上老师说"下周交实验报告"，当时记住了，两天后就忘了；
- 想查天气决定穿什么、要不要带伞，得切出聊天窗口、打开天气 App、再切回来；
- 做课程设计要整理待办清单、导出成文档交给组长，来回复制粘贴。

**共同点是：这些事情没有任何一件难，但每一件都要"人肉"在几个工具之间来回搬数据。**  
这正是智能体最擅长的场景——用户只负责用自然语言描述意图，剩下的判断和执行交给它。

### 1.2 用户画像与使用场景

| 项目   | 说明                         |
| ---- | -------------------------- |
| 目标用户 | 在校大学生（尤其是要同时应付多门课和小组作业的同学） |
| 使用场景 | 课间、宿舍、小组讨论中，想用一句话把琐事"甩出去"  |
| 使用方式 | 打开网页，说一句话，或按住麦克风直接说        |

### 1.3 功能需求

**F1 待办管理（核心）**

- F1.1 自然语言新增待办，自动解析优先级与相对时间  
  例："帮我记一下周三下午交软件工程实验报告，优先级高"  
  → 正文 `周三下午交软件工程实验报告`，截止 `2026-10-14`，优先级 `high`
- F1.2 查看待办清单，默认按「优先级 → 截止时间」排序
- F1.3 标记完成 / 删除待办

**F2 天气与出行建议**

- 输入城市名，返回实时天气 + 未来三天预报
- 自动给出可执行建议（带伞 / 防晒 / 加外套）
- 数据来自实时外部接口，而非预置数据

**F3 文件处理**

- 把待办清单导出为 Markdown 文件并真正落盘
- 读取、列出沙箱目录内的文件

**F4 通用能力**

- 数学表达式计算（安全的表达式求值）
- 获取当前日期时间，支撑"今天/明天/下周三"这类相对时间理解

**F5 对话与记忆**

- 多轮上下文记忆，重启浏览器后仍能恢复历史
- 前端提供语音输入与语音播报

### 1.4 非功能需求

| 编号 | 需求   | 说明                                      |
| -- | ---- | --------------------------------------- |
| N1 | 可演示性 | **没有大模型 API Key 也必须能完整跑通全部功能**，课堂演示不能翻车 |
| N2 | 易部署  | 核心功能零第三方依赖，`python server.py` 即可运行      |
| N3 | 安全   | 文件操作限制在沙箱内；计算功能不得使用 `eval`；密钥不进仓库       |
| N4 | 可扩展  | 新增一个工具只需写一个函数 + 一个装饰器                   |
| N5 | 可测试  | 工具层与智能体行为有自动化测试覆盖                       |

### 1.5 我们主动做的取舍

| 决策     | 选择                      | 理由                                                         |
| ------ | ----------------------- | ---------------------------------------------------------- |
| 大模型调用  | 直接用标准库 `urllib` 手写 HTTP | 避免依赖 `openai` SDK，任何 OpenAI 兼容服务（DeepSeek/通义/智谱/Ollama）都能接 |

| 语音方案   | 浏览器 Web Speech API      | 零后端成本，不用买第三方语音服务                                           |

## 二、业务流描述

### 2.1 整体交互流程

```
用户（自然语言 / 语音）
        │
        ▼
┌────────────────────────────────────────────────────────┐
│  Web 前端  web/index.html                               │
│  文本输入 or 语音识别(Web Speech API) → POST /api/chat   │
└────────────────────────────────────────────────────────┘
        │
        ▼
┌────────────────────────────────────────────────────────┐
│  智能体主循环  core/agent.py                            │
│                                                        │
│  ① 读取会话记忆 + 拼装系统提示词                         │
│  ② 送大模型，同时附上 10 个工具的 JSON Schema             │
│  ③ 模型判断：需要调用工具吗？                            │
│        ├─ 需要 → 执行工具 → 结果作为 observation 回填      │
│        │        → 回到 ②（最多 6 轮）                    │
│        └─ 不需要 → 直接生成自然语言回答                   │
└────────────────────────────────────────────────────────┘
        │
        ▼
┌────────────────────────────────────────────────────────┐
│  工具注册表  tools/registry.py                          │
│  待办 · 天气 · 文件 · 计算 · 时间                        │
└────────────────────────────────────────────────────────┘
        │
        ▼
前后端渲染：回答气泡 + 工具调用卡片 + 侧栏待办/文件刷新
```

### 2.2 三个典型业务的完整时序

**业务一：记录一条带时间与优先级的待办**

```
用户：帮我记一下周三下午交软件工程实验报告，优先级高
  │
  ├─ 前端 POST /api/chat {session_id, message}
  ├─ 智能体拼接 [系统提示词] + [历史记忆] + [本次输入]
  ├─ 大模型返回 tool_call: todo_add({
  │      text: "周三下午交软件工程实验报告",
  │      due: "2026-10-14",       ← 调 current_time 推出"周三"的具体日期
  │      priority: "high" })
  ├─ 工具层写入 storage/todos.json，返回 {"ok": true, ...}
  ├─ 结果回填给模型 → 模型生成口语化确认
  └─ 前端渲染："已经记下了 ✅ …" + 侧栏待办自动刷新
```

**业务二：查天气并给出行建议**

```
用户：我明天要去杭州，帮我看看天气，要不要带伞？
  │
  ├─ 大模型判断需要实时数据 → tool_call: weather_query({city: "杭州"})
  ├─ 工具层请求 https://wttr.in/Hangzhou?format=j1&lang=zh
  ├─ 解析 current_condition + 未来三天 weather 数组
  ├─ 按降雨概率自动生成建议（≥50% → "记得带伞"）
  └─ 网络不可用时降级为内置示例数据，并在 source 字段中明确标注"非实时"
```

**业务三：导出待办清单为文件**

```
用户：把待办清单导出成 Markdown 文件
  │
  ├─ tool_call: file_write({path: "待办清单.md", content: "..."})
  ├─ 工具层路径安全校验（禁止逃出 storage/workspace）
  ├─ 写入磁盘，返回字节数与内容预览
  └─ 前端提示"已保存到沙箱文件：待办清单.md（355 字节）"
     —— 用户可以去文件夹里真的看到这个文件
```

### 2.3 状态与数据流

| 数据     | 存储位置                                 | 生命周期           |
| ------ | ------------------------------------ | -------------- |
| 待办事项   | `storage/todos.json`                 | 长期，跨会话保留       |
| 对话记忆   | `storage/sessions/<session_id>.json` | 长期，按会话隔离，可手动清空 |
| 沙箱文件   | `storage/workspace/`                 | 长期             |
| 工具调用轨迹 | 随对话记忆一起持久化                           | 用于前端渲染工具卡片     |

**记忆的分层设计**（一个容易被忽略但很重要的细节）：  
对话过程中会产生三种中间消息——`assistant(tool_calls)`、`tool(result)`、`assistant(回答)`。  
如果把这些全部塞进长期记忆，一旦按轮次截断，就可能出现  
「有 `tool` 消息但没有对应的 `tool_calls`」的非法序列，直接导致接口报错。  
所以我们的做法是：**长期记忆只存 `user` 和最终 `assistant` 回答**，  
工具调用的中间消息只在单次请求内存在。这也是我们在开发中真实踩过的坑。

### 3.2 关键设计一：工具注册表——一处定义，三端复用

这是本项目最核心的设计。我们不想让"工具"这个概念和某一种框架绑死。

```python
@tool(
    name="todo_add",
    description="新增一条待办事项。当用户说'记一下''提醒我'时调用。",
    parameters={
        "type": "object",
        "properties": {
            "text": {"type": "string", "description": "待办内容"},
            "due": {"type": "string", "description": "截止时间 YYYY-MM-DD"},
            "priority": {"type": "string", "enum": ["high", "normal", "low"]},
        },
        "required": ["text"],
    },
)
def todo_add(text: str, due: str = "", priority: str = "normal") -> dict:
    ...
```

一个装饰器，就把普通 Python 函数变成了智能体可调用的工具。  
注册表随后可以导出成三种形态：

| 消费方        | 导出方法                    | 用途                                   |
| ---------- | ----------------------- | ------------------------------------ |
| 内置主循环      | `openai_tools_schema()` | OpenAI function calling 的 `tools` 参数 |
| MCP Server | `mcp_tools_schema()`    | MCP 协议的 `inputSchema`                |
| 测试 / demo  | `call_tool(name, args)` | 直接调用，便于单元测试                          |

**收益**：加一个新工具只需要写一个函数；MCP Server 是零成本附赠的。

### 3.3 关键设计二：ReAct 主循环

`core/agent.py` 的核心逻辑压缩后不到 40 行：

```python
messages = [{"role": "system", "content": SYSTEM_PROMPT}] + self.memory.history()

for _ in range(config.MAX_TOOL_ROUNDS):          # 最多 6 轮，防止死循环
    message = chat_completion(messages, tool_schemas)
    tool_calls = message.get("tool_calls") or []

    if not tool_calls:                            # 模型不再需要工具 → 输出回答
        return message["content"]

    messages.append({"role": "assistant", "tool_calls": tool_calls})
    for call in tool_calls:                       # 执行工具并回填结果
        outcome = call_tool(name, args)
        messages.append({"role": "tool",
                         "tool_call_id": call["id"],
                         "content": json.dumps(outcome, ensure_ascii=False)})
```

这就是智能体"能说会做"的全部秘密：**把工具描述塞进上下文，让模型自己决定调用时机**。

### 3.4 关键设计三：双模式运行，保证演示不翻车

考虑到课堂演示时可能没有 API Key、或者网络不稳定，我们设计了两条路径：

| 模式               | 触发条件              | 行为                        |
| ---------------- | ----------------- | ------------------------- |
| `llm`            | 配置了 `LLM_API_KEY` | 大模型 function calling，自主决策 |
| `rules`          | 未配置 Key           | 关键词规则路由到工具，功能完全可用         |
| `rules-fallback` | 配置了 Key 但接口报错     | 自动降级，并在返回值中带上错误原因         |

规则模式不是敷衍的"假回答"——它同样会真实调用工具、真实落盘文件、真实写待办，  
只是把"模型决策"换成了"正则匹配决策"。用户在前端可以看到当前处于哪种模式。

### 3.5 关键设计四：安全的文件沙箱

```python
def _resolve(relative_path: str) -> Path:
    candidate = (SANDBOX / relative_path).resolve()
    root = SANDBOX.resolve()
    if candidate != root and root not in candidate.parents:
        raise ValueError("路径越界：仅允许操作 storage/workspace 目录内的文件")
    return candidate
```

`resolve()` 会把 `../` 展开成绝对路径，再做前缀校验，  
所以 `../../evil.txt` 这类尝试会被直接拦下（有对应测试用例）。  
**智能体拿到了文件读写权限，就必须给它划边界**——这是我们做这个项目最大的安全意识收获。

### 3.6 关键设计五：不带 eval 的计算器

```python
tree = ast.parse(expr, mode="eval")   # 只解析，不执行
value = _eval(tree)                   # 递归白名单求值
```

只允许 `+ - * / // % **`、括号和 `sqrt/log/sin/cos/pi/e`。  
`__import__('os').system('rm -rf /')` 这种输入会被 AST 白名单直接拒绝。  
如果图省事用 `eval()`，一个聊天框就等于一个远程代码执行漏洞。

### 3.8 开发中真实踩过的四个坑

**坑一：天气描述返回英文。**

`wttr.in` 的 `lang=zh` 字段对于 "Smoky haze" 这类词条没有中文译文，  
直接取会得到英文。改用接口返回的 `weatherCode`（WW 天气码）查本地中文码表，问题解决。

**坑二：长期记忆截断导致接口 400。**

早期把工具调用的中间消息也写进了记忆，按轮次截断后出现孤立的 `tool` 消息。  
改为长期记忆只保留 `user` / `assistant` 两条记录。

**坑三：「记一下周三」被误读成「下周三」。**

正则写成 `(下周|周)\s*([一二三四五六日])`，结果用户说  
「帮我记一**下周三**下午交报告」时，"一下"里的"下"和"周三"被拼成了"下周三"，  
截止日期整整错了一周。修复方式是加负向后顾排除：

```python
r"(?:(?<![一以留剩了过再])(下|本|这)(?:个)?)?(?:周|星期|礼拜)\s*([一二三四五六日天1-7])"
```

**坑四（最有价值的一个）：「现在有什么待办」被凭空建成了一条待办。**

这是我们测试时真实发现的 bug，也是最能说明"智能体工程"难点的一个：  
用户问「现在有什么待办」，智能体却在清单里加了一条正文叫  
**"现在有什么待办"** 的新待办。截图如下：

```
用户：现在有什么待办
  ↳ 工具调用 todo_add({"text":"现在有什么待办","due":"","priority":"normal"})
  知行：已经记下了 ✅
        - 内容：现在有什么待办
        - 编号：#4
        - 当前还有 4 条待办未完成。      ← 它把自己也数进去了
```

**根因**：规则路由里"新增待办"的关键词表包含了 `待办`、`任务` 这些名词，  
而"查询待办"的关键词表只列了 `待办清单`、`查看待办` 等固定搭配。  
用户换个说法说成"**有什么**待办"，就匹配不上查询、反而撞上了新增。

**教训**：**在意图判定里，"名词"不能当作"动作"来用。**  
`待办` 只是话题域，不是动作；真正的动作是 `记一下`、`新增`、`提醒我` 这些动词。

**修复方案是把判定改成分层优先级**：

```python
# 强疑问信号（什么/哪些/多少/有没有/查看/看看…）→ 一律走查询，绝不新增
if any(k in raw for k in _QUERY_HINTS):
    return "todo_list", {}

if any(k in raw for k in _REMOVE_KEYS):     # 删除
    ...
if any(k in raw for k in _DONE_KEYS):       # 完成
    ...

# 新增必须同时满足：① 有明确写入动词 ② 正文不是问句
if any(k in raw for k in _ADD_VERBS):
    body = strip_meta(_strip_lead(raw))
    if body and not _is_question(body):
        return "todo_add", {...}

# 只有弱信号（如单独一个"待办清单"）→ 当查询处理
if any(k in raw for k in _WEAK_QUERY_KEYS):
    return "todo_list", {}
```

**修复后的效果**（我们为这批说法写了 10 条查询 + 5 条新增的回归测试）：

| 用户输入      | 修复前         | 修复后       |
| --------- | ----------- | --------- |
| 现在有什么待办   | ❌ 新增了一条垃圾待办 | ✅ 列出清单    |
| 待办清单      | ✅ 列出清单      | ✅ 列出清单    |
| 帮我记一下购物清单 | ❌ 生成帮助文本    | ✅ 新增      |
| 删除第2条     | ❌ 生成帮助文本    | ✅ 删除第 2 条 |


这件事让我们真正理解了：**智能体的工程质量，很大程度上不在大模型，而在意图边界的设计。**  
即使换成大模型模式，这个"名词不能当动词"的原则同样适用——  
我们在系统提示词里也补了一条"用户只是询问时不要调用工具"。

### 3.9 测试情况


## 七、每个小组成员的心得

> 本项目共 3 名成员，每人负责一条主线（内核 / 工具与前端 / 接口安全与文档），以下为各自的心得。

**邓子豪：第一次真正看懂"智能体"这三个字**

以前我以为"智能体"就是"更聪明的聊天机器人"。做完这个项目才明白，
关键差别在 **tools 参数**：把工具的 JSON Schema 塞进请求体，
模型就会在合适的时机吐出 `tool_calls`。所谓"自主决策"，
本质是"模型根据工具描述决定调哪个函数、传什么参数"。
我第一次看到日志里模型自己拼出 `{"city": "杭州", "due": "2026-10-14"}` 时，是真的有点震撼。
最大的坑是长期记忆截断导致接口报 400——排查了很久才发现是孤立的 `tool` 消息，
这也让我理解了 OpenAI 消息协议里 `tool_call_id` 的严格对应关系。
另外服务的部署也踩了不少坑：Windows 上 `pkill` 收不掉旧进程、端口被占用，
后来才学会用 `netstat -ano` 定位 PID 再精确结束——这些琐碎问题反而是最耗时间的部分。

**黄琪：自然语言解析比想象中难，把"能用"变成"好演示"更难**

我负责待办工具和前端界面，这两件事给我的感受刚好是"里子"和"面子"。
做工具时，我一开始觉得"把用户说的话存下来"就完事了。
结果测试时发现，"优先级高""周三下午"这些信息全被当成正文塞进了待办内容里。
后来写了 `resolve_due()` 处理相对时间、"明天/后天/下周三"，
写了 `strip_meta()` 把元信息从正文剥离，才真正可用。
这让我意识到：**智能体的体验好坏，很多时候不在模型，而在工具的参数设计**。
做前端时体会更深——功能做完了不等于作业做完了。
一开始界面只能把工具返回的 JSON 原样打出来，又长又难懂；
后来我把工具调用做成可折叠的卡片，默认收起只显示工具名和状态，
需要时展开看完整参数——这样演示时既清爽又能证明"真的调用了工具"。
语音功能用的是浏览器自带 API，零成本但效果意外地好，
答辩时可以现场对着麦克风说话，很有说服力。

**李文争：给 AI 权限之前，先给它划边界**

我负责文件工具、天气接口和这份随笔。写文件工具时第一反应是"直接 open() 就行"，
但转念一想——用户说一句"帮我删掉 D 盘那个文件夹"会怎么样？
所以加了沙箱校验，用 `resolve()` 展开路径再比对前缀，
还在测试里专门写了 `../../evil.txt` 的用例。
计算器也是同理，AST 白名单求值而不是 `eval()`。
**能力越大越要限制，这是这次作业给我最深的印象。**
写文档的过程又让我把整个项目重新梳理了一遍：
把一个 bug 的"现象 → 根因 → 修复 → 回归验证"完整写出来，
比我当初改代码时理解得还透彻——**写不清楚，往往说明还没真的搞懂**。

### 8.4 我们自己额外发现的三个"宝藏"

1. **wttr.in** —— 一个 `curl` 就能查全球天气的免费接口，  
   `?format=j1` 返回结构化 JSON 且**不需要申请 Key**。做演示项目时简直是救星。
2. **Web Speech API**（`SpeechRecognition` + `speechSynthesis`）——  
   浏览器原生，几行 JS 就给智能体加上语音输入输出，不用花一分钱买 TTS 服务。
3. **`ast` 模块做安全计算器** —— `ast.parse(mode="eval")` + 节点白名单，  
   是替代 `eval()` 的标准做法。这个技巧不止用于智能体，任何需要"执行用户表达式"的场景都用得上。

### 8.5 给下一届同学的一句话建议

**先跑通最小闭环，再谈框架。** 我们没有一开始就上 LangChain，  
而是先用标准库手写一遍"消息 → 工具 → 回填 → 回答"，  
看清楚每一步发生了什么，再去对比框架帮你省了什么。  
这个顺序会让整个作业从"抄一遍代码"变成"真的学会一件事"。
